PROJECT NOTE / LOCAL AI WORKSPACE

低配置运行大模型
从 8B 到 70B 的探索

AvaSubaru4862026 年 11 月 14 日项目介绍 · 技术详解

一台 i5-1235U、16 GiB 内存、Intel UHD 核显的 Windows 电脑，怎样完成大参数模型的本地推理？Local AI Workspace 把低比特量化、按需读取、内存预算和桌面交互放到同一个工作区，让每次尝试都有过程、有记录。

从一台已有的电脑开始

Local AI Workspace 面向普通 Windows 设备，关注有限内存条件下的大模型加载与运行。参考机使用 i5-1235U、16 GiB RAM 和 Intel UHD 核显，本版三档模型的文字路径采用 CPU 计算，独立显卡与大显存没有被列为这条路径的前提。

模型文件与运行依赖准备好后，回答由本机权重生成。应用负责把选择模型、输入问题、观察输出、取消任务和导出日志连接起来，让已有设备成为本地 AI 实验平台。

项目的核心问题包括：权重怎样表示得更紧凑，哪些数据需要同时留在内存中，模型切换后怎样释放资源，以及一次回答究竟花了多少时间。模型规模、运行速度、内存需求与回答质量，都需要留下各自的依据。

三档模型，各自怎样运行

项目配置了 Qwen3 8B、Gemma 3 27B 与 Llama 3.3 70B。模型清单固定了上游版本、具体文件、量化方式和 SHA-256，方便在相同权重上比较不同设备与运行参数。

模型量化权重体积文字运行路径
Qwen3 8BUD-IQ2_XXS2.61 GBCPU 内存映射
Gemma 3 27BUD-IQ1_S6.51 GBCPU 内存映射
Llama 3.3 70BUD-IQ1_S15.85 GB分层 CPU 读取

表格使用十进制 GB。70B 权重约为 14.77 GiB，已经接近参考机的整机内存；Windows、界面、上下文缓存与计算缓冲仍需要空间。27B 还配有约 0.86 GB 的视觉组件，原始完整便携 ZIP 连同运行环境约为 29.70 GB。

第一步：低比特量化

如果只按 70B 参数、每个参数使用 2 字节粗略估算，权重约为 140 GB，运行时还有额外的内存需求。本版 70B 采用 UD-IQ1_S 量化文件，将权重保存为约 15.85 GB，为普通设备上的存储和读取创造条件。

量化改变数值的表示精度，参数规模、文件体积与回答质量需要分别考察。UD-IQ2_XXS、UD-IQ1_S 是具体量化方案名称，实际文件还包含结构信息和其他开销，准确体积以模型清单的字节数为准。

低比特压缩也会带来精度取舍。项目后续需要用固定提示、成对任务和较长输出继续评估回答质量，再结合运行成本选择合适的模型。

第二步：存储、内存与 CPU 协作

SSD保存完整模型权重
→
有限内存容纳当前计算所需数据
→
CPU计算并逐步生成 token

8B / 27B：内存映射，按访问需求调入

两档文字路径把模型文件映射到进程地址空间，系统根据实际访问调入页面。配套低内存后端关闭整文件预取，应用按照启动时可用内存与设置计算驻留预算。

内存足够时，已经访问的页面可以留在内存中供后续计算使用；页面频繁被回收时，磁盘访问和等待就会增加。模型文件大小、映射的地址空间与此刻驻留的物理内存采用不同统计口径，需要通过实际工作集和系统剩余内存观察运行情况。

70B：分层读取，降低同时驻留需求

70B 使用原便携版配套的专用低内存 CPU 后端，按计算阶段读取各层权重。完整模型保存在 SSD，当前阶段需要的数据进入有限内存，再交给 CPU 计算。应用设置分层文件路径、无缓冲和直接读取请求，并从日志校验这条路径是否启用。

生成过程会继续经过模型各层，权重无法充分缓存时会反复读取文件。SSD 吞吐、读取延迟、CPU 负载与系统剩余内存都会影响等待时间。这种安排通过增加读取与等待，换取更低的同时驻留需求。

分层读取由配套后端执行，应用源码负责模式选择、预算与启用校验。复现时需要准备与清单匹配的低内存推理后端，公开源码仓库中的配置记录了这条运行路径。

第三步：管理任务与内存预算

启动前，应用读取系统可用内存和用户设置，分别计算模型的私有提交预算与驻留工作集预算。70B 的驻留配置上限为 4 GiB，默认模型进程提交预算为 12 GiB；两者描述不同统计口径，整机占用还包含系统、桌面界面、文件缓存与运行缓冲，实际数值需要结合日志分析。

模型及其子进程纳入 Windows Job Object 管理，运行期间持续观察内存；超出自身预算时结束任务并记录原因。切换模型、取消请求或退出应用时回收对应进程，减少大型模型同时占用资源的情况。

三档文字任务串行执行，默认最多 4 个推理线程、2048-token 上下文、每轮最多生成 256 个新 token。上下文还会占用运行缓存，长历史、长提示和长输出都会增加开销；实测部分使用的 512-token 上下文、64-token 输出上限单独记录。

  1. 检查模型文件、版本与可用内存，计算本次任务预算。
  2. 按模型选择内存映射或分层读取，启动对应后端。
  3. 观察回答、首字等待、生成速度与实际内存占用。
  4. 任务完成或取消后记录结束状态，切换时回收旧模型进程。
模型配置为 70B 标注了 24 GiB 起、32 GiB 推荐内存。16 GiB 参考机完成过下述短任务，属于受限条件实验；其他设备还需要结合可用内存、SSD 性能与具体任务验证。

把运行机制整合成可以操作的工作区

桌面端提供聊天、历史会话、附件输入和 Python 工作区；运行端组织模型配置、资源预算、文字与视觉路径，以及任务取消、切换和退出。项目的工程工作集中在把这些环节连接为完整流程。

Gemma 3 27B 使用配套视觉组件处理图片。视频通过 FFmpeg 最多抽取 6 帧，再把画面与采样时刻交给同一个 27B 模型。该路径分析抽样画面，不转写音频；已有两张简单图片样例通过测试，两次视频回答的完整性仍需改进。

基础模型来自 Qwen、Google Gemma 和 Meta Llama，量化采用 Unsloth 发布版本，推理依赖 llama.cpp 等上游组件。我的工作主要是桌面交互、运行路径组织、资源管理、离线集成与统一日志。

这组短任务展示了不同规模的等待和生成情况。70B 在参考机上完成了一次回答，首字前约等待 2 分 34 秒，整轮约 5 分半；按本次解码速度计算，平均每个输出 token 约需 17.5 秒。token 是模型处理单位，与中文字符之间没有固定的一对一关系。

这些记录可用于观察一次任务是否完成，以及等待主要出现在哪些阶段。要评价持续交互，还需要增加生成长度、重复固定提示，并分别记录冷启动、热启动与系统负载。低比特模型的回答质量也需要独立评估。

27B 4 token/s、70B 0.5 token/s 是后续优化目标。后续会结合磁盘读取、线程、上下文和内存记录定位瓶颈，再用多轮实验检查修改是否有效。

以上为作者提供的实机记录，本次文案更新未重新运行模型测速。比较时需要固定模型哈希、后端、提示、上下文与实际输出长度。

怎样根据任务理解“低配置运行”

轻量交互与流程验证：8B 权重较小，可作为观察聊天、任务取消、历史管理和资源回收流程的起点，再通过实际日志判断交互体验。

更大模型与视觉实验：27B 用来比较更大参数规模的运行开销，并结合配套视觉组件探索图片输入。输出质量与资源成本需要放在同一任务条件下比较。

受限内存中的 70B 实验：重点是大参数模型怎样加载、怎样完成推理，以及磁盘与内存如何配合。现有短任务记录显示等待较长，持续长文与多轮表现需要继续验证。

项目希望把模型规模、运行成本和任务效果放到同一张实验记录中。这样才能根据电脑和任务选择模型，再决定下一轮应调整参数、改进读取路径，还是增加硬件资源。

让每次运行都能留下依据

“导出运行日志 ZIP”生成 runs.csv、runs.jsonl 和字段说明，记录软件版本、设备、模型哈希、量化、token 数、首字时长、解码速度、内存和结束状态。聊天正文与附件保留在本机，不进入该统计包。

首字时长反映输出开始前的等待，解码速度反映生成阶段的表现，整轮时长反映一次任务从开始到结束的成本。结合驻留工作集、私有提交量与系统剩余内存，就能进一步分析加载、计算和读取之间的关系。

比较不同设备时，我会固定模型文件、后端版本、提示、线程、上下文和输出长度，再分别观察等待、速度与资源占用，把一次运行转化为可以复查的记录。

源码、指南与演示

仓库包含应用源码、配置、使用指南、技术文档和两段演示视频，可以通过“Code → Download ZIP”一次获取。模型权重、Python / Qt / CUDA 运行时、编译后的应用和原始 29.70 GB 便携包未随本次发布上传。

从源码运行时，需要根据依赖清单、模型配置与技术文档准备环境，并为低内存 CPU 路径配置匹配的推理后端。本站展示项目设计与实验过程，应用中的模型推理在本机执行。
